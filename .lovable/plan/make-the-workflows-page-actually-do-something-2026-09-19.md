# Make the Workflows page actually do something

## Where things stand (confirmed)

Yes — at this stage everything runs locally, with no real AI agents. The Loom modules and the "weave" step produce structured scaffolds from fixed rules written into the app, not model output. There is a switch in the code ready to point at a real engine later, and it is off.

The Workflows page is the thinnest part of it. Right now it only:
- lists 5 fixed templates (one per mode),
- lets you tick step checkboxes, which are forgotten on refresh,
- offers a single link back to Modes.

So your read is correct: choosing a mode and opening workflows leads to a dead end.

## What to build

1. **Persist workflow progress.** Ticked steps save locally per template, so returning shows where you left off, plus a small "2 of 4" progress line and a reset control.

2. **Connect each workflow to the Loom.** Every template gets a mapped Loom module (e.g. Build the spine -> Signal Collapse, Weave the threads -> Serendipity Lab, Draw the figure -> Creative Personas, Open the field -> Serendipity Lab, Run a loop -> Creative Operator). A "Run this in the Loom" button opens that module with the workflow's intent pre-filled, so the checklist ends in a produced artifact instead of nothing.

3. **Capture a closing note.** At the end of each workflow, one short free-text field ("what did this give you?"), saved locally and listed on the Snapshots page, so finished sessions leave a trace.

4. **Real exits, not just back.** Footer actions on the page: continue to the Loom, map a state, or return to modes — instead of the single back-link.

5. **Honest labelling.** A small line on the Loom and Workflows pages stating outputs are generated by local rules, not an AI model, with the seam noted for later.

## Technical notes

- Extend `src/lib/studio/store.ts` with `workflowProgress: Record<string, { steps: number[]; note?: string; updatedAt: string }>`; read/write through the existing local-first adapter.
- Add `moduleId` and a `seed` string to `WorkflowTemplate` in `src/lib/modes/workflows.ts`.
- `WorkflowTemplateView` becomes stateful against the store instead of local `useState`, and renders the Loom hand-off `Link` to `/loom/$moduleId` with the seed passed via search params.
- `loom.$moduleId.tsx` reads that search param to prefill its first longtext input.
- No backend, no network calls; `USE_REMOTE_LOOM` stays false.
